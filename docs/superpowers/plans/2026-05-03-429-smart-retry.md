# 429 Smart Exponential Backoff Retry Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development`
> Steps use checkbox (`- [ ]`) syntax.

**Goal:** 完善 429 智能指数退避重试模块，实现"429 比其他错误更值得多等几次"的策略。429 是限流错误，等待后极大概率成功，应该比普通错误重试更多次、退避更耐心。当前代码因 `WaitWith429Backoff` 方法未实现而编译失败，需要补全并统一 429 重试策略。

**Architecture:** 429 请求流：upstream 返回 429 → ratelimit 解析 Retry-After → 计算指数退避延迟（比普通错误更激进的多重试+更慢的退避增长）→ 等待并重发请求 → 更新 per-config cooldown 供并发请求共享。核心设计是 429 专用退避策略独立于普通错误重试，429 用 1.5x 增长+最多 8 次+90s 总预算，普通错误用 2x 增长+更少次数。

**Tech Stack:** Go 1.22, sync.Mutex, context.Context, regexp for Retry-After parsing

**Risks:**
- `WaitWith429Backoff` 方法不存在导致 client 包编译失败 → Task 1 必须首先实现该方法
- 429 重试可能被主重试循环和 429 专用逻辑双重执行 → Task 2 统一重试入口，429 走专用路径后 continue 主循环
- 流式请求的 context deadline 需要在 429 等待期间保持有效 → Task 2 使用 deadline-aware context

`WaitWith429Backoff` 只负责等待（不发请求），供 client 在自己的重试循环中调用。它解析 429 错误体中的 Retry-After，按 1.5x 指数增长计算延迟，带 jitter，总等待不超过 TotalWaitCap。

文件: `backend/ratelimit/limiter.go:160`（在 RateLimit429Config 定义之后添加）

```go
// WaitWith429Backoff performs smart 429-specific backoff waiting.
// Unlike ExecuteWith429Retry which wraps a function call, this method
// only handles the wait logic — the caller is responsible for making
// the actual request and detecting 429 errors.
//
// It parses Retry-After from the error body, applies exponential growth
// with jitter, and respects context cancellation. The per-config cooldown
// is updated so concurrent requests also benefit from the learned delay.
//
// Returns (result, nil) on normal completion, or (nil, ctx.Err()) if cancelled.
func (l *Limiter) WaitWith429Backoff(
	ctx context.Context,
	configID string,
	errBody string,
	cfg RateLimit429Config,
) (*RateLimit429Result, error) {
	// Parse Retry-After from the 429 error body
	delay := l.calculate429Delay(errBody, 0, cfg)

	// Update per-config cooldown so concurrent requests also wait
	l.Cooldown(configID, delay, "429 backoff")

	// Wait for the delay, respecting context cancellation
	t := time.NewTimer(delay)
	defer t.Stop()

	select {
	case <-ctx.Done():
		return &RateLimit429Result{
			Aborted:     true,
			Reason:      "context cancelled during 429 backoff",
			Attempts:    1,
			TotalWaited: 0,
		}, ctx.Err()
	case <-t.C:
		return &RateLimit429Result{
			Succeeded:   false, // We only waited — caller must re-execute the request
			Attempts:    1,
			TotalWaited: delay,
		}, nil
	}
}
```

```go
// calculate429Delay computes the wait delay for a 429 retry attempt.
// Uses upstream Retry-After as base, with exponential growth and jitter.
// Growth factor is 1.5x per attempt — gentler than 2x because 429s
// from rate limits are transient and more patience pays off.
func (l *Limiter) calculate429Delay(errBody string, attempt int, cfg RateLimit429Config) time.Duration {
	// Parse Retry-After from the error body
	upstreamWait := ParseRetryAfter(errBody)

	// Use upstream's suggestion as base, or fall back to BaseDelay
	delay := upstreamWait
	if delay <= 0 {
		delay = cfg.BaseDelay
	}

	// Apply exponential growth (1.5x per attempt)
	// 429 errors are transient rate limits — more patience = higher success rate
	// attempt=0: use upstream delay directly (respect the server's hint)
	// attempt=1: 1.5x, attempt=2: 2.25x, attempt=3: 3.375x...
	if attempt > 0 {
		growthFactor := 1.0
		for i := 0; i < attempt; i++ {
			growthFactor *= 1.5
		}
		delay = time.Duration(float64(delay) * growthFactor)
	}

	// Cap at MaxDelay
	if delay > cfg.MaxDelay {
		delay = cfg.MaxDelay
	}

	// Add jitter to avoid thundering herd
	if cfg.JitterFraction > 0 {
		jitterRange := time.Duration(float64(delay) * cfg.JitterFraction)
		if jitterRange > 0 {
			jitter := time.Duration(rand.Int63n(int64(jitterRange)))
			delay += jitter
		}
	}

	// Final cap
	if delay > cfg.MaxDelay {
		delay = cfg.MaxDelay
	}

	return delay
}
```

- [ ] **Step 1: Fix non-streaming 429 retry in CreateChatCompletion — 使用 WaitWith429Backoff 并与主重试循环协调**

当前非流式路径在遇到 429 时调用不存在的 `WaitWith429Backoff`，且等待后 `continue` 到主循环的下一轮，但主循环的重试计数也在递增，可能导致 429 还没等到足够次数就用光了普通重试配额。修复策略：429 等待不消耗主重试计数（429 有自己的 MaxAttempts 预算）。

文件: `backend/client/openai_client.go:544-558`（替换 429 处理块）

```go
				// For 429: smart multi-attempt exponential backoff
				// 429 is much more likely to succeed with patient retries than other errors.
				// We don't consume the main retry budget for 429s — they have their own
				// budget (RateLimit429Config.MaxAttempts=8, TotalWaitCap=90s).
				// This means a 429 wait + retry doesn't advance the main loop counter.
				if resp.StatusCode == 429 {
					ratelimit429Cfg := ratelimit.Default429Config()

					waitResult, waitErr := ratelimit.Global.WaitWith429Backoff(ctx, c.ConfigID, errorMsg, ratelimit429Cfg)
					if waitErr != nil {
						return nil, fmt.Errorf("cancelled while waiting for 429 backoff: %w", waitErr)
					}
					if waitResult.Aborted {
						logger.Warn("← [OpenAIClient] 429 backoff aborted after %v wait: %s", waitResult.TotalWaited.Round(time.Second), waitResult.Reason)
						return nil, fmt.Errorf("429 rate limit: %s (waited %v)", waitResult.Reason, waitResult.TotalWaited.Round(time.Second))
					}
					logger.Warn("← [OpenAIClient] 429 rate limit, smart backoff waited %v (config=%s, upstream_retry_after=%v)",
						waitResult.TotalWaited.Round(time.Second), c.ConfigID, waitResult.UpstreamRetryAfter.Round(time.Second))
					lastErr = fmt.Errorf("OpenAI API error (status 429): %s", classifiedError)
					// Don't advance attempt counter — 429 has its own budget.
					// The main loop will retry with the same attempt number.
					attempt--
					continue
				}
```

当前 handler 在流式请求前先检查 `ShouldReturn429Overload`（>60s 就拒绝），然后调用 `Wait`。但 `Wait` 只是被动等待已有的 cooldown，不能智能应对新发现的 429。优化：移除 60s 硬限制（让 429 专用退避策略自己管理预算），改用更灵活的等待逻辑。
